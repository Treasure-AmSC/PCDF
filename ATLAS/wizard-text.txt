## Wording shared by the wizards, kept once so every program says the same thing.
##
## Each entry starts with a line "@@ key" and runs to the next one. Blank lines
## around an entry are not part of it. Lines that start with "##" are comments.
## {{NAME}} marks a value that the program fills in.
##
## How entries reach each program:
##   Page, TUI, and generators  read this file directly (the page build embeds the
##                              entries its script uses in the page).
##   bundle.*                   README sections and converter notes, chosen when the
##                              script builds a bundle.
##   runner.*, manifest.*,      embedded in run-pcdf.py, make-manifest.py, and the
##   converter.*, common.*      converter as a MESSAGES dict ({{MESSAGES:prefix}}).
##   shell.*, dtn.*             inserted into shell scripts one entry at a time
##                              ({{@key}}).

@@ bundle.section-condor
HTCondor run
------------
1. Extract the bundle on a filesystem shared by the access point and execute
   nodes:
   tar -xf pcdf-ntuple-bundle.tar
   cd pcdf-ntuple
2. Check code/submit-pcdf-ntuple.condor. Its input manifest, converter, and output
   directory must be visible at the same paths on every execute node. The
   submit file does not copy DAOD inputs through HTCondor file transfer. Each
   execute node also needs `uv`, the Python script runner that runs the
   converter, on its PATH.
3. Start the included workflow:
   ./run-pcdf.sh
   It creates the manifest, asks before submitting, then follows all jobs in
   the cluster until they finish. Stopping the monitor does not remove jobs.
4. To run each step yourself, use code/make-manifest.py, condor_submit
   code/submit-pcdf-ntuple.condor, and condor_q.

Single machine without HTCondor
-------------------------------
When condor_submit is not on PATH, ./run-pcdf.sh offers to run the
conversions on this machine instead. Use ./run-pcdf.sh --local to do this even
when HTCondor is installed. This mode needs `uv` on this machine and does not
need HTCondor. This mode still reads the manifest, output directory, and CPU
cores per file from code/submit-pcdf-ntuple.condor, so keep that file in the
bundle. It runs as many conversions at once as the available cores allow. Each
conversion writes its output and error logs under logs/. Rerunning skips files
whose output is already complete.

@@ bundle.section-slurm
Perlmutter run
--------------
1. Copy this bundle to Perlmutter and extract it:
   tar -xf pcdf-ntuple-bundle.tar
   cd pcdf-ntuple
   The Python and SLURM scripts are marked executable.
2. On a login node, check the account, manifest, output directory, and node
   count in code/submit-pcdf-ntuple.slurm. The job writes all tables below the same
   output directory. It runs one file conversion on each physical CPU core.
3. Start the included workflow:
   ./run-pcdf.sh
   It creates the manifest, asks before submitting, then shows the queued,
   running, and completed job states. The job keeps running if you stop
   monitoring with Ctrl+C.
4. To run each step yourself, use code/make-manifest.py, sbatch
   code/submit-pcdf-ntuple.slurm, and squeue -u $USER.

The manifest helper can scan a directory populated by `rucio download`, or look
up a `scope:name` dataset at `NERSC_LOCALGROUPDISK`, a Rucio storage element.
For each replica it keeps only the local path, without the scheme, host, and
port of the replica PFN. It can also create a private ATLAS VOMS proxy, connect
to a NERSC data transfer node (DTN), and download a Rucio dataset into
`$SCRATCH` before submission. The login node and the DTN both read the proxy.
The batch job itself does not need Rucio.
